# Which APG patterns should be native / polyfilled platform features?

> Moved from effects-of-atmosphere `docs/research/` on 2026-10-23 with the widgets. `effects-of-atmosphere-xxxx` ids are beans in that repository.

Research for `effects-of-atmosphere-etfq`
(parent map: effects-of-atmosphere-0lab). Compiled **2026-10-03**. Reading only: no polyfill was installed into the
repo; the focusgroup polyfill tarball was unpacked in a temp dir to measure size and read its token table.

Method: browser versions come from **MDN browser-compat-data 8.1.4** (published 2026-10-01) and the
**webstatus.dev API** (live); spec status from the WHATWG HTML source (`main`), Open UI explainers (`main`),
chromestatus and the vendors' standards-position repos; polyfill facts from npm registry + GitHub APIs + READMEs.
Where a fact comes from a blog post rather than a primary source it is marked _(secondary)_.

## Recommendation legend

| Label        | Meaning                                                                                                                           |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **native**   | Use the platform feature directly. The library ships markup/ARIA wiring and at most a feature-detected fallback, no behaviour.    |
| **polyfill** | Consume an existing third-party polyfill that follows the spec. Library behaviour only fills documented gaps.                     |
| **library**  | No usable platform feature. The library owns the behaviour (Quint spec is the implementation source).                             |
| **hybrid**   | The platform covers part of the pattern (movement, overlay, disclosure). The library owns the rest (selection, typeahead, state). |

## Per-feature notes

### focusgroup

- **Spec**: Open UI explainer (last updated 2026-07-28) is the only document; WHATWG PR #11723 (opened 2025-09-29, still open). ARIA mapping lives in w3c/aria#2778 _(secondary)_.
- **Covers**: arrow-key directional navigation (logical axes, RTL/writing-mode aware), Home/End, guaranteed single tab stop per _segment_, last-focused memory (`nomemory` to disable), `wrap`/`nowrap`, `inline`/`block`, `focusgroupstart`, opt-out (`none`), nesting, shadow-DOM traversal, minimum role + child role inference on **generic** elements only.
- **Does not cover** (explainer non-goals and silence): selection (_"decoupled from selection"_), typeahead (not mentioned anywhere), `aria-activedescendant` focus models, activation (Enter/Space), expand/collapse, submenu keys, tree semantics, edit mode. Cross-axis keys are left free for the author.
- **Key conflicts**: native `<input>`, `<textarea>`, `contenteditable` etc. keep their arrows; authors can cancel with `preventDefault()` on `keydown`. Role inference never infers `menuitemcheckbox`/`menuitemradio`; `focusgroup="none"` items keep their own role (Roselli's tests, 2026-07).
- **V2** (explainer 2026-08-10): `itemcontrols`, `feed`, `grid` (rectangular, spanless; `treegrid`, virtualized and ragged grids are explicit future work).
- **Polyfill** `@microsoft/focusgroup-polyfill`: MIT, Microsoft, v1.6.0 (2026-07-30), ~1 release/month since April; full bundle 16.5 KB min / **5.5 KB gz**, shadowless 10.3 KB min / 3.7 KB gz; no dependencies. Tests: Playwright, ported from WPT `html/interaction/focus/focusgroup` (15 spec files incl. shadow, top-layer, dynamic changes) and also run against Chrome Canary, where the polyfill disables itself by feature detection. That is a good sign for spec fidelity. Known limits (README): rewrites `tabindex` attributes (saves and restores author values), no `focusGroup` IDL property on elements, does not observe visibility changes (workaround: `focusgroup="none"`), no `reading-flow` support, role inference only on `div`/`span`/custom elements, cannot see author key listeners, always polyfills `grid` even when native exists (unless `__FOCUSGROUP_POLYFILL_ALLOW_NATIVE_V2__`). Low-level `FocusGroup` + `FocusGroupItemCollection` exports let a framework hand over its own item list and call `update()`.
- **Integration constraints for a Solid layer**: (1) `tabindex` on items is owned by focusgroup, so never bind it reactively on the same node; (2) emit explicit roles ourselves (the polyfill and engines infer differently, and generic-only inference leaves `<button>` items implicit); (3) prefer the `FocusGroup` class over `polyfill()` + MutationObserver so Solid's reconciliation drives `update()`; (4) feature-detect with `'focusGroup' in HTMLElement.prototype` (polyfill 1.5.0 changelog; the Chrome RFC blog snippet used the lowercase name _(secondary)_ so verify on a real Chrome 150).

### popover and invoker commands

- Popover is Baseline; `popover=hint` (non-closing sibling popovers, built for tooltips) shipped C151 / F153. `ToggleEvent.source` C140 / F145 / S26.5. Invoker commands are Baseline since 2025-12-12; the built-in list is exactly the six in the WHATWG source. `commandfor` is intended to replace `popovertarget` (Open UI explainer).
- Gap versus APG menus: the platform gives top layer, light dismiss, Esc and focus restoration but nothing about menu semantics, typeahead, hover intent or submenus.
- Polyfills: `@oddbird/popover-polyfill` 0.7.3 (BSD-3, zero deps, Playwright tests, used by GitHub, caveats section on CSS/`:popover-open`); `invokers-polyfill` 1.0.4 (MIT, 21 KB, zero deps, **no test suite in the repo**, declared "feature complete"; its code uses the spec command names although its README still lists `open-popover`/`close-popover`).

### Interest invokers and tooltips

- `interestfor` on `<button>`/`<a>`/`<area>` fires `interest`/`loseinterest` on the target (hover or keyboard focus, delays through `interest-delay`), and shows/hides popover targets. Chrome/Edge 142 only; spec is WHATWG PR #11006 (open); Mozilla neutral, WebKit raised concerns including touch/device independence. Open UI says its design work is concluded and the work moved to WHATWG/CSSWG.
- Polyfill `interestfor` (Mason Freed, BSD-3): no implicit anchor, limited touch support, **manual tests only** (hover/focus cannot be automated). Fine as a progressive layer, not as a conformance oracle.

### dialog, closedby, details, until-found

- `<dialog closedby=any|closerequest|none>`, `requestClose()` and `:modal` are in the WHATWG source. `closedby` is still _preview_ in Safari; `requestClose` shipped S18.4.
- `<details name>` exclusivity is in the HTML spec and Baseline _newly_ (2024-09-03). Open UI graduated it. `w3c/html-aam#509` tracks group naming in the accessibility tree.
- `hidden=until-found` is in the spec; Safari 26.2 is _partial_ in BCD.

### Customizable select, combobox, listbox

- `appearance: base-select`, `::picker(select)`, `::picker-icon`, `::checkmark`, `<selectedcontent>`: Chrome/Edge 135, **Safari 27** (BCD, webstatus 2026-09-14), Firefox 149 behind a flag. Open UI graduated the explainer. Browsers without support render a plain `<select>`, so it degrades safely.
- Covers the **select-only combobox**. Editable comboboxes with a filtered list are not covered: Open UI _combobox_ (input + `<datalist>` + `beforefilter`, `:filtered`) and _filterable select_ (WHATWG issue #12050) are Chromium-flag prototypes with several competing syntaxes.
- `<select>` itself already provides typeahead; focusgroup `listbox` does not.

### CSS carousels

- `::scroll-button()` creates real `<button>`s; `::scroll-marker` creates `<a>`-like markers in a `::scroll-marker-group` that Chrome exposes like a tablist with focusgroup-like keyboard behaviour (Chrome blog, 2025-03-20 _(secondary)_). Chrome/Edge only, experimental in BCD.
- APG carousel also requires a rotation control, auto-rotation pause on hover/focus and slide labelling, none of which CSS provides. Hence **hybrid**.

### Switch

- `<input type=checkbox switch>` shipped in Safari 17.4 (WebKit blog 2024-02). Chrome's stated objections in WHATWG PR #9546 were an unstyleable control and an under-specified rendering model; a Chromium _Intent to Prototype_ appeared in July 2026 _(secondary)_. MDN now documents it as experimental. The attribute is ignored by other browsers, so a checkbox + `role=switch` is the safe baseline.

### Anchor positioning

- Core shipped in all three engines (C125 / F147 / S26). `@oddbird/css-anchor-positioning` 0.10.2 is BSD-3, depends on floating-ui, css-tree, nanoid, has a WPT runner and Playwright e2e, and is only applied below Chrome 125. Caveats: no implicit anchors (name anchors explicitly), `position-area` is emulated with a wrapper element, dynamic content only partly handled.

### ARIA reflection, referenceTarget, ariaNotify

- Element-reflecting ARIA properties are shipped in all engines (S16.4 / F136 / C135). That is enough to wire `aria-activedescendant`, `aria-controls` and `aria-labelledby` across shadow roots **imperatively**; Chrome still lacks `ariaOwnsElements`.
- `referenceTarget` (declarative cross-root ID references) is Chrome/Edge 152 only, non-standard-track in BCD, WHATWG PR #10995 open: do not depend on it.
- `ariaNotify()` is Baseline _newly_ since Safari 27 (2026-09-14).

### Open UI element proposals (no implementations found)

`<menubar>/<menulist>/<menuitem>/<submenu>`, `<toolbar>`, `<tabs>` (editor's draft), `<rangegroup>`, press buttons (toggle), openable API. None ships; none has a polyfill. Treat them as hints about where focusgroup-style attributes may be superseded, not as targets.

### Bottom sheet / sheet (not an APG pattern)

- **Not in APG.** The Patterns index has no sheet, drawer or bottom-sheet entry; a sheet is a presentation of **Dialog (Modal)**. Dialog semantics (`role=dialog`, `aria-modal`, focus trap and return, Esc, inert background, `::backdrop`) come from the native dialog or popover; position, slide, snap, drag handle and stacking are presentation only.
- **Native stack**: `<dialog>` + `showModal()` (or `popover`) for the semantics, `scroll-snap-type: y mandatory` + CSS scroll-driven animations for the snap points, `scrollsnapchange` (with an `IntersectionObserver` fallback) to read the snap state and `scrollIntoView` to set it. No polyfill needed. Safari 18.2+ is the floor for the initial-snap technique.
- **`pure-web-bottom-sheet`** (MIT, web component, "near zero JS") is exactly this composition and delegates **all** accessibility to the native dialog/popover — it ships no `role` and no `aria-*`. Read it as evidence that the semantics belong to the platform, not as a library to adopt.
- **React Aria Components 1.22.0** (2026-10-08) shipped `Sheet` on the same basis: native CSS scroll snap + view timelines on top of its existing `Modal`, not a new primitive.
- **Recommendation: native composition, no primitive.** `dialog-modal` already carries the semantics, and the snap index / `sheetState` is a reading of the browser's scroll position, not a machine. See [bottom-sheet.md](bottom-sheet.md); a headless `sheet` snap-value primitive is captured as a conditional, low-priority bean (`effects-of-atmosphere-aztx`).

## How a Quint spec should treat a natively provided behaviour

This is a recommendation derived from the findings above and from the repo's rules (spec is source of truth;
generated machine is differentially tested; "a machine exists only where state changes over time").

1. **Spec the contract the user sees, not the provider.** The APG keyboard/ARIA contract is the invariant. Whether movement comes from native focusgroup, the polyfill or library code is an implementation choice recorded as metadata (`provider: native | polyfill | library`), not as a different spec.
2. **One shared platform-contract module per native feature**, written once (for example `focusgroup`: owner, items, segments, memory, axis, wrap, one tab stop per segment; `popover`: open/closed, light dismiss, Esc, focus return; `invoker`; `details-group`). Pattern specs **import** it and model only the **delta**: tabs = focusgroup(tablist) ∘ selection machine; menu-button = popover ∘ menu keys. Platform transitions appear in the pattern spec as environment events (`FocusMovedByGroup`, `LightDismiss`, `CloseRequest`) that the pattern asserts on but does not implement.
3. **Record the contract gap explicitly.** Each hybrid pattern lists what the platform does _not_ do (typeahead, selection, `activedescendant`, submenu keys). Those gaps are exactly the library's machine. Example: `listbox-typeahead.qnt` is entirely a gap spec; the movement part is the platform contract.
4. **Test the polyfill and the native engine against the same oracle.** The microsoft polyfill already shows the method: its tests are ported WPT cases and also run on Chrome Canary, where the polyfill disables itself. For us: replay the same Quint-derived traces in (a) Chromium with the polyfill forced, (b) Chromium 150+ native, (c) our Solid layer. A divergence is either a polyfill bug (report upstream) or a contract gap (add to the gap list). The spec-only test (simulation + invariants) stays as is; platform behaviour is checked in a real browser (Playwright), never in a DOM mock.
5. **Generate library code only for the gap machine.** For natively provided transitions the generated model is an oracle for the differential test, not an implementation target. Do not hand-write resolvers for behaviour the platform owns.
6. **Pin unstable contracts.** focusgroup is an explainer-level spec (grid unreleased, `itemcontrols` unsupported, WHATWG PR open). Put the explainer date, polyfill version and WPT commit in the platform module header, the same way upstream test sources are pinned in the scenarios README, and bump deliberately.
7. **Feature detection is part of the spec boundary.** Model "provider available?" as a boot-time constant so a spec trace can run with and without it. It also lets a plugin (atproto component) declare required platform features.

## Findings that change the plan

- **focusgroup is real but narrow**: shipped only in Chrome/Edge 150, no WHATWG text, WebKit not signed on. Its polyfill is high quality (MIT, 5.5 KB gz, WPT-derived tests). It replaces roving-tabindex code for toolbar, tablist, radiogroup, listbox, menu, menubar. It does **not** replace selection, typeahead, activedescendant or tree/grid behaviour.
- **The overlay layer is now Baseline**: popover, invoker commands, `<dialog>` (+`closedby` outside Safari), `<details name>`, `:open`, anchor positioning (3 engines), `ariaNotify` (since 2026-09-14). The library should not reimplement overlay stacking, light dismiss, focus trap, or exclusive accordion.
- **Several headline features are still single-engine**: `interestfor`, CSS carousels (Chromium), `<input switch>` (Safari), customizable select (Chrome + Safari 27, Firefox flag), `referenceTarget` (Chrome 152). They need `@supports`/feature detection and a working fallback.
- **No platform story at all** for treeview, treegrid, multi-thumb slider, window splitter, feed (V2 only), editable combobox, typeahead (anywhere). These are the library's real surface.
- **Do not rely on elements that exist only as Open UI explainers** (`<menulist>`, `<toolbar>`, `<tabs>`, `<rangegroup>`).
- **A sheet needs no primitive**: it is Dialog (Modal) — already native via `dialog-modal` — plus native scroll snap. React Aria Components 1.22.0 shipped its `Sheet` the same way, on its existing `Modal`, so the library-majority rung agrees: document the composition, do not add a primitive.

## Unverified / follow-ups

- Chrome 150 token support is taken from secondary sources (EMIT, Roselli, web.dev); the focusgroup tokens and role inference should be re-verified in a real Chrome 150+ before the platform contract module is frozen.
- No Chromium implementation status was found for Open UI menu elements; no Firefox position was checked for `interestfor` beyond the closed _neutral_ issue (#1181).
- Gecko/WebKit implementation plans for focusgroup are unknown (positions only).
- Not evaluated: ariakit/Base UI/React Aria use of these features; that belongs to the scenario-mining tickets.
